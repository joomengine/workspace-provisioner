# External operator configuration

The public package provides the engine, validation rules, generic workload definitions and examples. It does not select an operator's production JCB version, carry their branding, or contain their Composer credentials. Keep all deployment configuration outside the checkout and release directory. The JSON files must be regular files owned by the operator (or root), mode 0600, below trusted directories that other users cannot write. Symlinked configuration paths are rejected.

## Create the configuration directory

Prepare a private inventory with `hosts` and `profiles`, a private catalog mapping names to approved images, and an authenticated Incus client configuration. `examples/inventory.lab.json` illustrates the inventory structure only; its documentation addresses are not a deployable network. Copy and configure it outside the checkout for your own isolated environment.

Use `php bin/workspace help` for the complete CLI. `configure --directory DIR --inventory FILE --catalog FILE --incus-config DIR` creates a **new** owner-only directory, encryption key, credential store and `operator.json`. All supplied paths must be absolute. It refuses an existing destination. No VM or network is created by this command. Never put the resulting directory beneath this repository or a web root.

`php bin/workspace validate --config FILE` validates the operator document and recipes. Workspace submission also checks any Composer inputs before reserving the workspace. `state:migrate --config FILE` initializes the operation store. The file driver is appropriate for a single trusted management machine; use the PostgreSQL driver for an operational database. Preserve the store and master encryption key in protected backups. Losing the key prevents recovering protected credentials and encrypted archives.

## Operator document, version 1

| Section | Required contents |
| --- | --- |
| `version`, `installation_id` | Schema version 1 and an installation UUID, generated by `configure` |
| `state` | `driver: file` with an absolute `path`, or `driver: pgsql` with `dsn`, `username` and `password_file` |
| `vault` | Absolute owner-only `directory` and `key_file` |
| `incus` | Absolute `binary` and protected client `config_directory` |
| `hosts` | Approved independent Incus remote/project/network/storage inventory |
| `profiles` | Resource profiles selected by name, not arbitrary customer resource values |
| `catalog` | Named VM/container and optional recipe/Composer selections |
| `callers` | Named trusted service roles with allowed `tenants` and `actions` |
| `recipe_secrets`, `backup_directory` | Absolute private directories |
| `image_resolver` (optional) | Absolute Skopeo `binary`, default `/usr/bin/skopeo`, and optional private `auth_file` |

Unknown fields fail validation. A caller label scopes authorization; it is **not** an authentication credential. The local caller must already possess trusted OS access. A remote HTTP service must authenticate and establish the caller server-side rather than accepting an arbitrary customer-provided caller label.

PostgreSQL credentials belong in the password file, not the DSN or command line. Configure verified TLS in the DSN for remote database connections and limit the database role to the provisioner's state schema. Schema migration is a separate administrator step; ordinary workers do not create database tables implicitly.

Each host entry requires `remote`, `project`, `network`, `storage`, `bridge_address`, `addresses`, `ingress`, `dns`, `denied`, `cpu_budget`, `memory_mib_budget`, and `disk_gib_budget`. Use dedicated projects, existing approved storage pools, distinct non-overlapping address pools, and ingress CIDRs that do not contain customer addresses. `denied` must include management destinations, including publicly addressed management services. The current policy uses explicitly approved public IPv4 DNS servers; private DNS exceptions are not silently added. Hosts are independent Incus endpoints, not an implicit clustered scheduler.

A resource profile requires `cpu`, `memory_mib`, `disk_gib`, `network_mbit`, and `io_mib`. Budgets and profiles are operator policy, not customer request fields. The allocator retains retired names and addresses to avoid accidentally reusing stale external routes. Pool expansion/retirement is an explicit administrative decision.

## Image selection and latest

Every catalog entry requires `vm_image`, `jcb_image`, `database_image`, `development_image`, `uid`, and `gid`. `vm_image` is a qualified Incus VM image fingerprint. Container selectors accept an explicit tag, including `latest`, or an immutable `@sha256:` reference. There is no production JCB image/version hardcoded in the controller. Public CI has separate, synthetic test-image choices.

For floating tags, install Skopeo on the management machine. The resolver fetches the registry's manifest/index over verified TLS and records the exact digest in the workspace operation store **before** creating the VM. Compose receives those immutable references. Retrying an interrupted operation, resuming a suspended workspace, or restarting a container does not resolve `latest` again. New workspace requests may resolve a newer digest. Explicit digest configurations do not need Skopeo to resolve a tag.

The JCB and development images must be a compatible, tested pair. The included development image is derived from the selected JCB image and uses UID/GID 33; arbitrary IDs require a correspondingly built image. Selecting independent floating tags does not guarantee they contain compatible PHP builds. Readiness checks reject a mismatch rather than expose a broken workspace.

The optional resolver auth file authorizes the management-side registry lookup only. It is never sent to the VM. Guest image pulls must independently be possible under the chosen delivery policy; the current pull path requires guest-readable images and does not implement a global private-registry credential handoff. Do not solve a private-image delivery requirement by copying infrastructure-wide registry credentials into customer VMs.

Changing the contents of an existing catalog/recipe or host definition is rejected for an already reserved workspace. Use a new catalog name for deliberate configuration changes and retain the old entry for existing workspaces. A tag moving remotely does not change the saved configuration hash, so it does not break established workspaces.

The provisioner's `latest` **release package** is separate from an operator's JCB `latest` **container selector**. See [releases](releases.md) for version resolution, checksums, publication and rollback.

## Private Joomla and VM recipes

A catalog may include an absolute `recipe` path. Omitting it selects the standard empty customization recipe. The document has `version: 1`, an `id`, and an ordered `steps` array. Each step requires `id`, `target`, `argv`, `timeout`, `repeat`, and `check`; optional keys are `depends_on` and `stdin_secret`.

`target: vm` runs a trusted VM-local helper before application initialization. Its executable must be listed in the catalog's `vm_executables` map with its approved SHA-256 digest. General interpreters and runtime/privilege managers are not accepted as VM recipe helpers. Such helpers run with guest management authority and must not execute website-controlled code. They never run on the physical compute host.

`target: joomla` invokes the selected JCB container's PHP and Joomla CLI as the workload UID/GID. Its `argv` starts with the Joomla command name, followed by separate arguments. No shell expansion, pipelines or interpolation are performed. These steps follow Joomla/JCB installation and optional Composer bootstrap. Check the selected JCB image's CLI help; do not assume that every JCB release provides identical command names.

`check` contains an argument array and may require exact trimmed `stdout`. A zero exit status and the optional expected output define the postcondition. `repeat: safe` permits a bounded retry after inspection; `repeat: once` prevents automatically repeating a step whose previous outcome is ambiguous. Dependencies refer to earlier step IDs. Each timeout is bounded and private command output is suppressed. A referenced stdin secret is read from `recipe_secrets` and sent only to the targeted operation.

Initialization recipes cannot run after customer handover. A resumed workspace is not rebranded, reimported or reinstalled. Separate authorized maintenance is required for subsequent modifications; passing a different initialization recipe is not an upgrade mechanism.

## Private workspace Composer files

The package's own `composer.json` and `composer.lock` belong to the provisioner. They are distinct from the optional workspace dependency files supplied by the operator.

A catalog's optional `composer` object requires these fields:

| Field | Meaning |
| --- | --- |
| `manifest`, `manifest_sha256` | Absolute path and exact SHA-256 of the external `composer.json` |
| `lock`, `lock_sha256` | Absolute path and exact SHA-256 of the matching external `composer.lock` |
| `directory` | `.` or a relative directory under `/var/www/html`; traversal and symlinks are rejected |
| `auth_secret` (optional) | Name of an owner-only Composer authentication JSON file under `recipe_secrets` |
| `timeout` (optional) | Overall helper limit in seconds; default 600, maximum 1800 |
| `dev` (optional) | Include development dependencies; default false |
| `replace` (optional) | Explicitly replace differing existing manifests; default false |

Input digests are checked before deployment and again when used. Missing/mismatched locks fail rather than run `composer update`. The bootstrap validates the lock, performs `composer install`, checks platform requirements and confirms an autoloader exists. Plugins and scripts are disabled. The operation uses a disposable, non-root dependency container with no SSH ports, Docker socket, root privileges, or infrastructure credentials. Composer authentication is delivered through stdin to temporary files inside that container; the container is removed on completion/failure. It does not remain a workspace service.

The default refuses to overwrite Joomla's own root Composer files with a different application manifest. Choose a subdirectory for independent dependencies, or explicitly approve replacement after testing compatibility. Installed packages and application manifests are customer-readable workspace files; private input storage is not a promise that deployed application code will be hidden from the customer. Never embed credentials in those manifests.

The maximum input sizes are 256 KiB for the manifest, 512 KiB for the lock, 64 KiB for authentication, and 1 MiB for the encoded combined request. Oversized configuration is rejected explicitly, not truncated.

## Generated Docker Compose configuration

Compose definitions are generated from the approved catalog, resources and network identity. The generator controls mounts, privileges, secrets, ingress ports and container users. There is deliberately no arbitrary customer/operator Compose overlay that can silently remove those security boundaries. Optional customizations use the documented recipe and Composer contracts instead.

Only per-workspace generated configuration enters the VM. Operator inventory, Incus credentials, unrelated recipes, registry credentials and other customers' data never enter the shared Joomla directory or a release artifact.
